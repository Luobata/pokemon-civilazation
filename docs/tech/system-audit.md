# 系统审计与后续推进

## 访问

运行 `npm run dev` 后访问 `/audit.html`。游戏底部「开发、命令回放与调试 → 系统说明与审计后台」会在新标签页载入点击时的当前对局副本。直接访问使用固定种子的默认测试局，也可导入游戏导出的 JSON 存档。

每个系统有稳定地址，例如 `/audit.html?system=s1-map`。左侧检索支持名称、实现状态和规则文字。规则目录及源码依据位于 `src/audit/catalog.ts`，当前数据由 `src/audit/inspect.ts` 查询实际状态和规则定义。

## 每个系统的审计合同

1. **规则说明**：描述已经执行的规则、审计关注点与实现依据。
2. **当前数据**：展示该系统的指标和完整开发数据，包括玩家正常视野以外的数据。
3. **系统调试**：提供相关命令的表单、条件预检查和真实执行，记录引擎事件或拒绝原因。
4. **覆盖状态**：明确标记已实现、部分实现或待实现；未实现系统不提供虚假生效按钮。

以后每次新增系统，同一改动必须更新规则目录、数据检查器、适用命令和必要的验证用例。设计文档和目录不能代替实际引擎实现。

## 沙盒行为

- 审计页在独立内存中调用正式 `step` 引擎，命令使用当前行动文明及真实命令序号；规则约束仍然生效。
- 「检查条件」执行纯计算，不提交结果，不改变 RNG、命令序号或撤销历史。
- 「AI 决策一步」使用当前文明的普通 `PlayerView` 生成一条 AI 命令，也可代理人类文明作诊断。其他文明不会自动整轮行动，便于逐步观察。
- 「结束当前文明回合」仅推进一位文明；所有文明结束后按正式规则触发轮结算。
- 每一步可撤销，最多保留 30 步；本页显示最近 60 条尝试。完整已接受命令仍保存在导出的副本日志中。
- 生产表单会把整条队列替换成所选一项。高级 JSON 支持完整 `orders`；字段形状校验后仍由引擎判断是否合法。
- 重置恢复本次导入的基线。导入失败保留原副本。审计操作不写入游戏的 localStorage 存档，也不回传原游戏标签页。
- 「导出副本存档」可以在游戏里手动导入继续；「导出审计记录」包含所选系统说明、指标、操作记录和完整存档，便于复现。

## 按顺序推进

| 顺序 | 工作 | 当前交付 / 验收条件 |
| --- | --- | --- |
| 1 | 固化上一轮成果 | `00b0758` 保存建筑、领袖、UI 与测试；本地独立开发分支 |
| 2 | 完整浏览器回归 | 上一轮 49/49 通过；新功能加入后必须再次完整回归 |
| 3 | 领袖数值证据 | 受控种子、座位轮换、相同性格的对局模拟；记录样本边界，再决定是否调数值 |
| 4 | 审计基础与质量覆盖 | 每系统说明、检查数据、沙盒操作；构建、lint、单元及浏览器验证；独立代码审查。中央语义检查缺失必须明示 |
| 5 | 领袖深化 | 主动技能、冷却、独特单位/建筑、性格差异；先定义行动消耗、存档和回放合同，再实现 |
| 6 | 后续版本玩法 | 按 `mvp-gdd.md`、`extension-design.md` 和审计目录中标记的版本推进图鉴/起源/冠军、信仰、暴走与双属性等系统 |
| 7 | 工程扩展 | 联机与服务端、性能专项、内容编辑器按各自验收合同推进 |

此页是推进顺序与审计使用说明。待实现条目表示缺口，不表示该系统已经开发完成；数值观察报告也不表示已完成长期平衡校准。
